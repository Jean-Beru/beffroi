# Architecture

The full design document lives with the project documentation; this page is the part a contributor needs.

## Packages and layers

```
src/core      heidi/core            identity core, pure PHP
src/oidc      heidi/oidc            OAuth 2.0 / OpenID Connect module, pure PHP, depends on the core
src/symfony   heidi/symfony-bundle  Symfony integration, depends on both
apps/op       heidi/op              the application, depends on the bundle
```

Inside each pure-PHP package, four layers checked by Deptrac:

| Layer | Contents | May depend on |
|---|---|---|
| `Domain` | Model objects, value objects, invariants, typed exceptions | PHP, PSR-20 |
| `Port` | Interfaces to the outside: repositories, signing, hashing, clock, events | `Domain` |
| `Application` | Use cases, one per endpoint or interaction step | `Domain`, `Port` |
| `Bridge` | Implementations of the ports on a third-party brick (jwt-library, key-management) and in-memory adapters for tests | everything above |

The core never depends on a protocol; protocols never depend on each other; nothing below the bundle sees Symfony's HTTP, DI or Doctrine. SAML and SCIM, when they come, are modules next to `heidi/oidc`.

## The identity core

- `Tenant`: an issuer, its keys, its users, its clients. The issuer URL may carry a path.
- `User`: a stable `subject` distinct from the technical id, so that an import from another IdP keeps its `sub`. Standard profile claims. `emailVerified` is a boolean, never a string.
- `Credential`: N per user, a kind being a class and nothing else. `PasswordCredential` carries a typed `PasswordHash` (algorithm and parameters). `PasskeyCredential` carries the credential record of WebAuthn Level 3 (credential ID, COSE public key, sign count, transports, backup flags, AAGUID, a 64-byte random user handle shared by the passkeys of a user, never the `sub` nor the e-mail) with the name the user gave it; what an assertion proves is read from its flags into `amr` values (`hwk` or `swk` by the backup eligible flag, `user` by user presence, `mfa` by user verification), a sign count that did not grow is an event, not a refusal. What a kind can do is an interface: `RevocableCredentialInterface` (a passkey; a password is replaced, not revoked), `ExternallyIdentifiedCredentialInterface` (found by what a party presents, the credential ID). Enrolment is `CredentialEnrolmentInterface`, two steps, one implementation per kind (`PasskeyEnrolment` over the `PasskeyRegistrarInterface` ceremony); `PasskeyAuthentication` opens a session on a verified assertion (`PasskeyAuthenticatorInterface`); `CredentialRevocation` revokes any revocable kind. The ceremonies themselves are the bundle's, over webauthn-lib. `TotpCredential` (RFC 6238, one active per user) carries the shared secret sealed by the KMS of the tenant, the last accepted time step so that a code is accepted once, and ten hashed backup codes spent once; it declares `SecondFactorCredentialInterface`: while a user holds an active one, a password alone signs nobody in (`SecondFactorRequirement`), the session of the core is opened only once the code passed, with `pwd` and `otp` at once (`TotpEnrolment`, `TotpAuthentication`, `ActiveTotp`; the attempts at a code are limited before anything is verified). The attempts at a password are limited the same way, per user and never per address (`PasswordAttemptLimiterInterface`, consumed by `PasswordAuthenticator` once the user is named and before the hash is verified; a refused attempt still pays a hash, a correct password empties the count, an unknown username is counted nowhere). The hash a refusal pays when no hash of the user can be verified, the user unknown, without a password or past the limit, is `DecoyHash`: one per process, produced by the hasher of the day from a value nobody knows, so that a refusal costs what a wrong password costs and the time says nothing of whether the account exists (decision 0006); the one decoy for `PasswordAuthenticator` and for the firewall of the bundle.
- `LinkedIdentity`: an identity at an upstream provider. `Group` and `GroupMembership` carry a `source` (local, upstream claims, SCIM); the source wins over manual edits.
- `AuthenticationSession`: who is authenticated, since when (`auth_time`), how (`amr`, and `acr` computed from the proofs: `"1"` for a password, the numeric level Keycloak emits by default, never stored nor configured) and from where: two `RequestContext` (creation, last seen) with IP, user agent, and later GeoIP and device. Sessions end one by one.
- Signing keys: `SigningKeyProviderInterface` gives the active key and the publishable set of a tenant. The private key is sealed as a `symfony/key-management` envelope, under a KMS key named from the tenant, and exists in clear only in process memory; web-token/jwt-library signs. A signature algorithm is a class behind `SignatureAlgorithmInterface`, one per algorithm, that names itself on the wire, says which kind of key pair it signs with and which digest `at_hash` and `c_hash` halve; RS256 (mandatory, OIDC Core §15.1), PS256, ES256 and EdDSA over Ed25519 are wired, and `SignatureAlgorithmsInterface` is the one source of truth over them: the keys that are generated, the JWS that are signed, the names a client may register and what the discovery document announces all read it, so a fifth algorithm is a class and a line in the wiring. A tenant holds one key per algorithm it signs with, and the JWK Set publishes them all. The KMS keeps, it does not sign: with Vault Transit, the Transit key of the tenant (`heidi-<slug>`, derived, not exportable) wraps the data key of each envelope, the private JWK never reaches Vault, and the credential of the OP is a token whose policy (`docker/vault/heidi-op.hcl`) grants data keys, decryption and the reading of the key configuration under the `heidi-` prefix, nothing else; with AWS KMS, the key behind `alias/heidi-<slug>` does the same through `GenerateDataKey` and `Decrypt`, the AAD as `EncryptionContext`; with the file backend, a sodium key in a file of its own, outside the sealed keys, does it in the process. The DSN is the only difference between the backends, and the bundle suite runs against each of them. A key is staged (published, signs nothing), active, retiring (published while what is bound to it can still arrive, its retirement date computed from the kinds of artifact the tenant binds to a key of that use, `KeyBoundArtifactInterface`: the ID token, the self-contained access token, the signed authorization response and the logout token for a key that signs, each saying its own lifetime where that lifetime is set), then retired; `TenantKeyRotator` drives the four states, a compromised key leaves the JWK Set at once.
- Events: every event carries `occurredAt`, the tenant and the `RequestContext` of the request that produced it.

## The OIDC module

- `Client` with exact-match redirect URIs, the secret in the shape the method it registered verifies against, the keys it publishes (`jwks` or `jwks_uri`), what names it in the certificate it presents (one of the five values of RFC 8705 §2.1.2), `requiresConsent` and `requiresPkce` per client (the latter false only for a confidential client).
- Client authentication: one class per method behind `AuthenticationMethodInterface`, tagged into the wiring, and an authenticator that knows none of them. `client_secret_basic`, `client_secret_post`, `private_key_jwt`, `client_secret_jwt`, `tls_client_auth` and `self_signed_tls_client_auth` (RFC 8705 §2, the certificate read with pki-framework, the chain judged at the edge) and `none` are wired. What a method reads of the request is its own to say, so the two mutual-TLS methods reading the one certificate of the connection are one mechanism of RFC 6749 §2.3 and not two, the registration of the client saying which of them verifies it.
- `AuthorizationRequest` validated in two stages: client and redirect URI first (errors are shown, never redirected), everything else after (errors are redirected with `error`, `state`, `iss`).
- A request that did not come as a query is turned into one before the parser sees it, by a resolver of its own: `PushedAuthorizationRequestResolver` for a request the client pushed (RFC 9126 §4), `RequestObjectResolver` for one it signed (RFC 9101 §6.1, `request` and `request_uri`). The parameters of the object are the request and the ones of the query are dropped (OIDC Core §6.1); the signature is verified against the keys the client publishes, under the algorithm it registered in `request_object_signing_alg`, with the reader and the verifier `private_key_jwt` uses. A `request_uri` is read back only from a URL the client registered, over one GET that follows no redirect. An object with `alg: none` is read from a client that registered `none` and from no other, and is asked for none of the claims that bound a proof, since it proves nothing.
- `Interaction`: the authorization endpoint parks the request; the integration authenticates and asks for consent; `AuthorizationHandler::begin()` returns `LoginRequired`, `ConsentRequired` or `Granted(code)`.
- Grants: `authorization_code` with PKCE S256 and replay detection, `refresh_token` with rotation and reuse detection, `client_credentials` for a client acting for itself, and `urn:ietf:params:oauth:grant-type:device_code` for what has no browser (RFC 8628). One class per grant, named by the grant and not by an enum; what a grant does with a refresh token, with a user and with a browser it declares by the interfaces it implements, and `ServedGrants` is that wired list, read by the endpoint, by a registration and by the discovery document.
- The device flow (RFC 8628, BCP 10027): `/device_authorization` answers an authenticated client two codes, where its user goes and how often it may poll; `/device` is the one screen, where a signed-in user types the code and confirms it explicitly, nothing being approved on a GET. The grant answers `authorization_pending`, `slow_down` with a growing interval, `expired_token` and `access_denied`, and spends the device code once.
- Tokens: access tokens in the shape the client is registered for (`access_token_format`: `at+jwt` verified offline, or opaque, a random value whose record the provider keeps hashed and removes on revocation). A shape is one class that writes it and one that reads it back, both answering to the name the issuer gives it and both tagged into the wiring; `ServedAccessTokenShapes` is that wired list, the one source of truth over the shapes, which a registration reads to know what a client may name and which the retirement of a signing key reads to know what is still being written, and `AccessTokenVerifier` refuses a wiring where a shape is written and read back by nobody. ID tokens with `at_hash` and `sid`, opaque refresh tokens stored hashed. What the client proved beyond being itself travels with the authorization as a `ConfirmationInterface` and binds the tokens of that request to it: the certificate of the connection (`x5t#S256`, RFC 8705 §3.1) or the key a proof was signed with (`jkt`, RFC 9449 §6.1), one class per kind and `Confirmations` the only place the member names are written down. The binding is the `cnf` of an `at+jwt`, a column of the record of an opaque one, and a member of the introspection response; a token bound to a key says so in `token_type` and is presented under the `DPoP` scheme from then on. A request that proves two possessions is refused rather than arbitrated, and the refresh token of a public client keeps what got it (RFC 9449 §5), a confidential one keeping none since its credentials are asked for at every refresh.
- Proof of possession (RFC 9449): `DpopProofVerifier` reads the `DPoP` header with the reader every JWT a client signs is read with, verifies the signature against the public key of the proof's own header (`ProofKeyVerifierInterface`, nothing looked up anywhere) and hands back the key named by its RFC 7638 thumbprint; `DpopProofValidator` asks the proof what request it was made for (`htm`, `htu` compared with the URL the provider publishes and never with a header of the request, `iat` inside a window, `jti` remembered for that window, `ath` naming the very token presented) and a nonce when the deployment wires one (`DpopNonceInterface`, `NoDpopNonce` by default). It is verified at the token endpoint, at the pushed endpoint, where it reserves the code for the key (`dpop_jkt`, §10.1), and at UserInfo, the first protected resource; introspection and revocation authenticate a client and take no proof.
- Discovery, JWKS with several keys, UserInfo (a bound token honoured only for a request that proves again what it is bound to, the challenge naming the scheme that would have worked), introspection (RFC 7662, signed when asked, RFC 9701) and revocation (RFC 7009) for what can be revoked, RP-Initiated Logout revoking the session's refresh tokens and opaque access tokens. `AccessTokenVerifier` hands a token to the wired verifier that recognises it, whatever shape it was written in, `AccessTokenInspector` adds the grant and user checks the provider's own resources make.
- The access token store is `AccessTokenRepositoryInterface`; what a store can revoke is declared by the companion interfaces it implements (`CanRevokeAccessTokenInterface`, `CanRevokeAccessTokensByGrantInterface`, `CanRevokeAccessTokensBySessionInterface`), which the callers ask with `instanceof`.

## The bundle

- Routes belong to one of two planes, and the route name says which: `heidi_interaction_*` (browser: authorize, login, consent, logout, device, account) and `heidi_protocol_*` (server to server: discovery, jwks, token, userinfo, introspect, revoke, par, device_authorization). `HEIDI_PLANE` makes a process refuse the routes of the other plane, so that an attack on login cannot take the token endpoint down.
- Messenger with RabbitMQ: three buses (`command.bus` transactional, `query.bus`, `event.bus`), three AMQP transports by priority, `failed` on Doctrine, everything synchronous in tests. The core's PSR-14 events are replayed on `event.bus`.
- Time does its part through `symfony/scheduler`: the schedule `heidi` (transport `scheduler_heidi`, consumed by the worker next to the buses, one process for it) recurs `AdvanceKeyLifecycle` every minute, routed like any command, whose handler activates the staged keys whose delay elapsed and retires the keys past their retirement date. The console does the same by hand: `heidi:keys:rotate` (stages, `--now` or `--compromised` activate at once), `heidi:keys:activate <kid>`, `heidi:keys:retire <kid> [--force]` or `--due`, `heidi:keys:list [--all]`; every one names the operator in the `RequestContext` of the events it dispatches. The staging delay is `heidi.keys.staging_delay`, by default the JWK Set max-age plus the 60 s refetch cooldown of `oidc_login`: the max-age is what a relying party fetching from the OP needs (its copy has expired when the key signs, measured by `castor demo --rotate`), the cooldown the margin for one served by a shared HTTP cache, which refetches on the unknown `kid` once its copy is that old and refuses the token before.
- Doctrine XML mapping of the pure classes, tables prefixed `heidi_`, `tenant_id` everywhere.
- Own user provider and form login on the bundle's identity store; never the host application's `User`. A passkey login and the second step of a password login (the code of an authenticator app or a backup code, on `/login/code`) are two more authenticators of the same firewall; between the password and the code the firewall holds no token, only a pending login in the HTTP session, five minutes. The passwords tried on a user through the firewall are counted by the same limiter of the core as `PasswordAuthenticator` counts them, before the hash is verified (`PasswordAttemptListener` on `CheckPassportEvent`), never by Symfony's `login_throttling`, which also counts per address and refuses an organisation behind one; the two limiters, codes and passwords, are declared by the bundle in the framework (five in a sliding minute, sixth refused) and tuned by no application. The firewall pays the same decoy hash as the core where it refuses a password before any hash (`RefusalCost` over `DecoyHash`): an unknown username, which the provider refuses before anything is hashed (`DecoyHashListener` on `CheckPassportEvent`, before the user checker), a user without a password, which `CheckCredentialsListener` refuses on the null hash (the same listener, before the hash), and an attempt too many (`PasswordAttemptListener` itself); an empty password, which Symfony refuses before any hash for a known user, costs nothing for an unknown one either. The pages of the account (`/account`, `/account/passkeys`, `/account/two-factor`, the QR code drawn by the bundle as an SVG, the backup codes shown once) read the session of the core. `/account` is the home they hang from, and what it offers is the sections that are wired, one per page, each saying what that account holds there: a page added to the account is a class beside the others and a line in the wiring, and the home page names no kind of credential. It is the one page of the account that sends a browser without a session to the login rather than refusing it, since there is somewhere to come back to (`LoginTarget`). The root of the application is the application's own, never the bundle's: `apps/op` redirects `/` to the home of the account because its issuer is the origin alone, under a route name that carries the interaction plane.
- Translations `en` and `fr`; the locale of an interaction comes from `ui_locales`, then `Accept-Language`, never from the URL.
