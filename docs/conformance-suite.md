# Conformance suite

The OpenID Foundation conformance suite is the external judge of spike 1, and of every certification profile the OP answers since. It runs locally from the prebuilt images of `registry.gitlab.com/openid/conformance-suite`, pinned by version in `compose.yaml`.

```bash
castor start --conformance
castor logs conformance-server
```

Then open https://localhost:8443 (self-signed certificate of the suite's nginx). `castor start --conformance` recreates the `op` container with `APP_PROFILER=0`: a plan of a hundred requests has no use for a hundred profiles, and the toolbar has no place in the pages the scripted browser reads. `castor start` alone puts the profiler back.

The three clients of the suite receive access tokens in the shape `CONFORMANCE_ACCESS_TOKEN_FORMAT` names (`jwt` by default): `castor start --conformance --access-token-format opaque` recreates the `op` container with opaque ones, and the plans must be green with either, since the suite presents the access token to UserInfo without looking at it. Both switches are environment variables of the container, documented in `apps/op/.env`.

## How the suite reaches the OP

- The `op` service has the network alias `op.localhost`, so the suite container resolves it like your browser does.
- Caddy issues the OP certificate from its internal CA. The suite container starts with `tests/conformance/server-entrypoint.sh`, which imports that CA into the JVM truststore before launching the suite exactly as the upstream image does. Everything else in the entrypoint is the upstream command line.
- Verified: a Java `HttpsURLConnection` from the suite container to `https://op.localhost` completes the TLS handshake.

## Gotchas met while wiring it

- The MongoDB property of the jar is `spring.data.mongodb.uri`.
- `SPRING_PROFILES_ACTIVE=dev` avoids the suite login, but the Google and GitLab OAuth registrations must be non-empty placeholders or Spring refuses to start. This mirrors the official `docker-compose-prebuilt.yml`.
- The nginx image proxies to `http://server:8080`: the server service needs the network alias `server`.
- The scripted browser of the suite runs inside the server JVM and follows the OP's redirect to `https://localhost:8443/...`, which is the container itself: the `conformance-redirector` sidecar (socat, same network namespace) forwards that loopback port to nginx, and the entrypoint imports the self-signed certificate of nginx into the JVM truststore next to the Caddy CA.
- An empty `POST` to `/api/runner` must not be sent as a form: Spring answers 415 to `application/x-www-form-urlencoded`, which Symfony's HttpClient adds by default.
- Starting a module answers the module as the suite renders it, and sometimes fails to render it: the scripted browser of the previous one is still landing, and the state the answer is built from is not finished being written (`Could not write JSON: null`, a 500 while the module starts all the same). The start is judged on the state of the module and never on that answer.

## The certification plans

Twelve runs of nine plans and one module on its own, one configuration, one task. `castor conformance` runs them all; `--plan basic`, `--plan config`, `--plan form-post`, `--plan rp-initiated-logout`, `--plan front-channel-logout`, `--plan back-channel-logout`, `--plan fapi2-security-dpop`, `--plan fapi2-security-mtls`, `--plan fapi2-signing-dpop`, `--plan fapi2-signing-mtls`, `--plan fapi-ciba-poll`, `--plan fapi-ciba-ping` or `--plan rotate-keys` (repeatable) runs one. A plan the suite has to be created twice with, once per set of variants, is two runs and two entries of the task: the alias of the configuration is exclusive, so a run is a plan with its variants and nothing else.

`--reset` empties the database of the OP before the plans run and provisions it again, then restarts the containers and waits for the discovery document: the plans were written against the OP `castor provision` leaves, a development user with a password and nothing else. A second factor or a passkey enrolled by hand, which a run of `castor demo --passkey` or an afternoon on the account pages leaves behind, stops the scripted browser of the suite on the page that asks for it, and every module of every plan then fails on the same line, `unexpected url for task: Verify complete`. The restart is not decoration: a worker of FrankenPHP holds the kernel and the opened signing key for every request it serves (architecture §3.3), and a worker that was up before the tables went keeps a key no row names any more. Nothing of the configuration is lost, the client secrets living in `apps/op/.env.local` and the clients in `apps/op/config/packages/heidi.yaml`.

The alias of the configuration is exclusive: two `castor conformance` at once on the same suite interrupt each other's modules with `Stopping test due to alias conflict`, and a `--reset` under a run in progress takes the tables from under it. One run at a time.

### Basic OP

`oidcc-basic-certification-test-plan`, created with `server_metadata=discovery` and `client_registration=static_client`. Its modules carry their own variant: all `client_secret_basic` except `oidcc-server-client-secret-post`, all `response_type=code` and `response_mode=default`. The plan needs three registered clients: `client` and `client2` in `client_secret_basic` (the second is the wrong client of some modules) and a `client_secret_post` one, because a client authenticates with the one method it registered.

The clients are registered in `apps/op/config/packages/heidi.yaml` (development only): `conformance-basic`, `conformance-basic-second` and `conformance-post`, all three with `requires_pkce: false`, the named exception of decision 0008 of the design repository: the Basic OP profile sends no `code_challenge` (one module out of thirty-five does, and it passes with the exception in place, since a challenge the client sends is verified all the same). Their secrets are generated by `castor provision` into `apps/op/.env.local` (`CONFORMANCE_BASIC_SECRET`, `CONFORMANCE_BASIC_SECOND_SECRET`, `CONFORMANCE_POST_SECRET`). The plan must use the alias `heidi`: the registered redirect URI is `https://localhost:8443/test/a/heidi/callback` and the post-logout one `https://localhost:8443/test/a/heidi/post_logout_redirect`. The user to sign in with is `alice`, password `HEIDI_DEV_USER_PASSWORD` of the same file; `castor provision` gives her every claim of OIDC Core §5.1 (`heidi:user:profile`), because the `oidcc-scope-*` and `oidcc-claims-essential` modules check that UserInfo answers each scope with its claims and end in a warning for a user without them.

### Config OP

`oidcc-config-certification-test-plan`, no variant, one module: `oidcc-discovery-endpoint-verification` reads the discovery document and checks it against OIDC Discovery §3. No browser, no client. It passed the day it was first run, on the document the Basic OP plan already read.

### Form Post OP

`oidcc-formpost-basic-certification-test-plan`, created with `server_metadata=discovery` and `client_registration=static_client`, the Basic OP plan run again with `response_mode=form_post`: the same modules, the same three clients, the same user, and an answer the OP gives as a page whose form the browser posts to the redirect URI instead of a redirection (OAuth 2.0 Form Post Response Mode §2). Nothing else moves: the profile is Basic, so its modules ask for `response_type=code` and no other, and an error of the authorization endpoint comes back posted like a success (OIDC Core §3.1.2.6).

The scripted browser needs nothing added: the page it receives submits itself, HtmlUnit running its one script, and the `Verify complete` task of the `browser` section waits for the callback of the suite as it does after a redirection. The page carries a `Content-Security-Policy` of `default-src 'none'` naming that script by hash; HtmlUnit does not enforce CSP, so the policy is judged by the functional tests of the bundle, not by the suite.

The suite creates 35 of the 38 modules the plan lists for these variants. One of them, `oidcc-unsigned-request-object-supported-correctly-or-rejected-as-unsupported`, was listed as known until spike 5 brought request objects (issue heidi#161, RFC 9101): the module writes `response_mode=form_post` only inside the request object it sends, never in the query, and the OP refused the object unread (`request_not_supported`, OIDC Core §6, which the module accepts as a rejection) so the refusal went back in the default mode and the form post checks of the callback failed. The OP now reads the object: `conformance-basic` registers `request_object_signing_alg: none`, the named exception of decision 0006 that lets an unsigned object be read, and the mode written inside it is the mode the answer uses. The line of `known` is deleted with it, which is what issue heidi#142 asked for; the plan is run again with the other three by issue heidi#166.

### RP-Initiated Logout OP

`oidcc-rp-initiated-logout-certification-test-plan`, created with `response_type=code` and `client_registration=static_client`; its eleven modules run with `client_secret_basic` on `client`. One checks the discovery document (`end_session_endpoint`), ten sign in through the authorization flow then call the end session endpoint: the nominal request (verified `id_token_hint`, registered `post_logout_redirect_uri`, `state`) and the same without `state` must land on `https://localhost:8443/test/a/heidi/post_logout_redirect`; a request with nowhere to go (`no-params`, `only-state`, `no-post-logout-redirect-uri`) must end the session and show it; a request that cannot be honoured (`post_logout_redirect_uri` not registered or with a query added, `id_token_hint` modified or issued to no client, `post_logout_redirect_uri` without `id_token_hint` or `client_id`) must show an error page and redirect nowhere (RP-Initiated Logout 1.0 §2, §3). The OP needed nothing for it: a verified hint ends the session and redirects at once, an unverified request goes through the confirmation page, every refusal is the `Request refused` page. Eight modules end in `REVIEW`, the screenshot of the page shown.

### Front-Channel Logout OP

`oidcc-frontchannel-rp-initiated-logout-certification-test-plan`, created with `response_type=code` and `client_registration=static_client`; two modules, the verification of the discovery document (`frontchannel_logout_supported`, `frontchannel_logout_session_supported`) and a sign-in followed by an RP-initiated logout whose page must load the logout URI of the client in an iframe, with `iss` and `sid`.

It is served by a client of its own, `conformance-front-channel-logout`, which registers a front-channel logout URI and nothing of the other channel. The suite certifies one channel at a time: a client that registers a logout URI is told at every logout of its sessions, and a module of another plan then fails on a request it did not expect (`Got an HTTP request to 'frontchannel_logout' that wasn't expected`). The metadata being per client, the three logout profiles take three clients.

### Back-Channel Logout OP

`oidcc-backchannel-rp-initiated-logout-certification-test-plan`, the same variants and the same shape: the verification of the discovery document, and a module that signs in, logs out and waits for the logout token at an endpoint of its own while it runs. Its client is `conformance-back-channel-logout`, which registers `backchannel_logout_uri` and `backchannel_logout_session_required`.

It is the one plan the OP answers from outside a browser, and the only one whose result depends on the worker: the token is minted on the event of the session ending and posted by a consumer (architecture §4.9, §5.6), so the latency of that queue is a matter of conformance and not one of operations. The URI the suite gives its clients names `localhost:8443`, which from inside the worker is the worker, and curl resolves every name ending in `.localhost` that way too, without reading `/etc/hosts`. The `conformance-worker-redirector` sidecar of `compose.yaml` therefore shares the network namespace of the worker and forwards that loopback port to nginx, as `conformance-redirector` does for the scripted browser of the suite, and `docker/worker/entrypoint.sh` fetches the self-signed certificate of nginx and adds it to the trust store of the container, as `server-entrypoint.sh` adds it to the truststore of the JVM. A worker that restarts leaves the sidecar forwarding nothing, and a worker that is recreated takes the identifier of the namespace with it, so the sidecar is created again behind the worker and never merely restarted (`compose_recreate_worker_redirector`): a restart forwards nothing at best and fails outright at worst, `joining network namespace of container: No such container`.

### FAPI 2

`fapi2-security-profile-final-test-plan` and `fapi2-message-signing-final-test-plan`, each created twice, once per pair of mechanisms the profile lets an authorization server choose between: `client_auth_type=private_key_jwt` with `sender_constrain=dpop`, and `client_auth_type=mtls` with `sender_constrain=mtls`. The other variants are the same for the four runs, `openid=openid_connect`, `fapi_profile=plain_fapi` and `authorization_request_type=simple`; Message Signing adds `fapi_request_method=signed_non_repudiation` and `fapi_response_mode=jarm`, which is what it has that the Security Profile does not: the request signed for non-repudiation and the answer signed (JARM).

Four clients serve them, two per pair, because a handful of modules present an authorization code or a request URI issued to another client: `conformance-fapi-private-key-jwt` and `conformance-fapi-private-key-jwt-second`, `conformance-fapi-mtls` and `conformance-fapi-mtls-second`, registered in `apps/op/config/packages/heidi.yaml` like every other development client. They carry what the profile asks and nothing of what the six OpenID Connect plans are allowed: no secret at all, `require_pushed_authorization_requests: true`, PKCE kept, and `ES256` registered for the ID token, for the authorization response and for the request objects, because the profile refuses RS256. The second client of each pair registers the callback of the suite twice, bare and with the query the happy flow pushes back to it (`?dummy1=lorem&dummy2=ipsum`): a redirect URI is compared byte for byte (decision 0006), so a query the client will send is a registration of its own.

Their keys are generated by `castor provision` into `var/conformance/`, one P-256 key each, and published to the provider as the public half of the set, base64 in `apps/op/.env.local` (`CONFORMANCE_FAPI_PRIVATE_KEY_JWT_JWKS` and the three others). The suite holds the private half. The two mTLS clients publish their certificate in the `x5c` of that key, which is what `self_signed_tls_client_auth` authenticates against (RFC 8705 §2.2), and the certificate is issued on the very key the set publishes, so one key serves the handshake and the signature of a request object. Nothing of that is committed.

The tenant holds an `ES256` signing key beside the `RS256` one it signs with by default: `castor provision` generates the keys of `DEV_KEY_ALGORITHMS` when the tenant publishes none for them, and a client that registered an algorithm the tenant has no key for is answered nothing.

A run that binds its tokens to a certificate calls the token, the PAR and the resource endpoints on `https://mtls.op.localhost`, the host whose listener asks for one (RFC 8705 §5, `HEIDI_MTLS_ORIGIN`, `docs/mtls-at-the-edge.md`); a run that binds them to a key calls the ordinary host. The resource a module calls with the token it obtained is the UserInfo endpoint, which is the protected resource an OpenID Provider serves (OIDC Core §5.3).

The four runs leave one module unpassed, the same one each time: `fapi2-security-profile-final-test-claims-parameter-identity-claims`, which reads the ID token of a request carrying a `claims` parameter and warns on every claim it does not know. The one it does not know is `sid`, which names the session the token was issued in. An OP that announces `frontchannel_logout_session_supported` or `backchannel_logout_session_supported` puts `sid` in the ID tokens it issues (Front-Channel Logout 1.0 §3, Back-Channel Logout 1.0 §2.1), and this one announces both as soon as it serves the channel; the claim is registered in the IANA "JSON Web Token Claims" registry by Front-Channel Logout 1.0 §6.1.1, and the list the suite checks an ID token against (`ValidateIdTokenStandardClaims`) does not carry it. The module is a check behind its own specifications and not a gap of the provider: dropping the claim would contradict the metadata the provider publishes, and would take from the logout endpoint what tells it that an `id_token_hint` describes the session in front of it (architecture §4.9). It is therefore listed under `known` for the four runs, with that reason and issue heidi#210, and the gap is written down whole: the module is known to end in `WARNING` on the one condition `CheckForUnexpectedClaimsInIdToken`. Its result is reported as `KNOWN` and accepted only when the run is exactly that; a failure, a second condition warning beside that one, or the module passing, fails the run, so that a regression on a module left open stays visible and the four lines are deleted rather than carried.

### FAPI-CIBA

`fapi-ciba-id1-test-plan`, created twice, once per delivery mode: `ciba_mode=poll` and `ciba_mode=ping`, the other variants the same for both runs, `client_auth_type=private_key_jwt`, `fapi_ciba_profile=plain_fapi` and `client_registration=static_client`. It is the certification plan of the one flow where the client never has a browser: it asks for a user it names, the user answers somewhere else, and the client learns it by asking again (poll) or because the provider called it back (ping).

Four clients serve the two runs, two per run: a client registers one backchannel token delivery mode (CIBA Core §4), so the modes cannot share theirs, and a module that signs a request object as the wrong client needs the second one. `conformance-ciba-poll`, `conformance-ciba-poll-second`, `conformance-ciba-ping` and `conformance-ciba-ping-second` in `apps/op/config/packages/heidi.yaml`, registered for the CIBA grant and for `refresh_token`, with `ES256` for the ID token and for the request objects and no redirect URI at all: there is no browser of the client anywhere in this flow, and the one page it has is a page of the provider. The two of the ping run register `backchannel_client_notification_endpoint`, the endpoint the suite serves under the alias of its configuration.

Two modules of each run carry the TLS checks of FAPI 1, and what they run them against is the resource the configuration names, twice: the checks read an accounts resource endpoint and an accounts request endpoint, which a configuration outside Open Banking names neither of, and each one falls back to `resource.resourceUrl`. That URL is the UserInfo endpoint on the mTLS host, so the two are the same host measured twice, and a finding of either is reported by both. The listener of the development stack offers the cipher suites §8.5 permits and no other and serves the RSA certificate they are authenticated by, which is a property of the Caddy the application image ships with and not of the provider (`apps/op/frankenphp/Caddyfile`, [Security defaults](security-defaults.md)); a deployment terminating TLS elsewhere answers for its own edge.

They authenticate with `private_key_jwt` and present a certificate all the same. FAPI-CIBA is a FAPI 1 profile, which asks for sender-constrained access tokens whichever way the client authenticated: the suite therefore calls the token endpoint on the mTLS alias (RFC 8705 §5) and refuses to configure a static client of this plan without `mtls.cert` and `mtls.key`. `castor provision` issues that certificate on the very key the client publishes, as it does for the mTLS clients of FAPI 2.

What a client names its user with is the `login_hint` of CIBA Core §7.1, read by this tenant as the `sub` the provider issued (§15 asks for an identifier that says nothing outside the provider, which a `sub` is and a telephone number is not). It is the one value of these runs that follows the rows rather than a file: `castor provision` reads it from `heidi:user:show` and writes `HEIDI_DEV_USER_SUBJECT` into `apps/op/.env.local`, so a database emptied and provisioned again publishes the new subject.

Nobody is in front of a screen when the suite runs, so the suite is given a URL to post the answer of the user to, its `automated_ciba_approval_url`, and substitutes the identifier of the request and the answer it wants into it (`{auth_req_id}`, `{action}`). What answers there is an endpoint of the bundle an application imports in development only, under a prefix of its own, exactly as it imports the endpoints of the FIDO2 server API: `/ciba/conformance/approval`. It signs the user in with their password and then answers with the two calls the approval page answers with, so it holds nothing the page does not: a session is opened on a proof, and a request made for somebody else is not in the list it reads. Without it every module of the plan waits five minutes for a human.

The two runs do not pass. Measured on suite 5.2.1 on 2026-09-27 on the maintenance branch after the merge ([run 36327346424](https://github.com/beffroi-php/heidi/actions/runs/36327346424)), the poll run ends in 26 `PASSED`, 6 `FAILED` and 3 `SKIPPED` of its 35 modules, the ping run in 25 `PASSED`, 11 `FAILED`, 1 `WARNING` and 3 `SKIPPED` of its 40. The three skipped in each are refusals of `RS256` the suite does not play when the variant sends no client assertion of that algorithm. What the rest stop at is five rules, four of the provider and one of what this file hands the suite. Two of them the provider follows since.

The first is the `x-fapi-interaction-id` of FAPI 1.0 Advanced Final §6.2.1, which every answer of a protected resource of the provider carries: the UUID the request named when it named one, one drawn for it when it named none, served or refused (issue heidi#315). FAPI 2.0 dropped that header, so none of the four FAPI 2 runs looks for it and these two runs are where it is judged.

The second is the suites a connection below TLS 1.3 can be negotiated with, where the rule is the listener's certificate as much as its cipher list. `DisallowInsecureCipher` opens a TLS 1.2 handshake offering every code point but the four §8.5 permits, and fails the run on whichever one the listener accepts; the four permitted are all authenticated by an RSA certificate, and the ECDSA certificate Caddy issues by default leaves the `TLS_ECDHE_ECDSA` suites as the only ones negotiable, which that list does not hold. The listener serves an RSA certificate and offers the two permitted suites Go implements since, and no handshake of the check completes (issue heidi#316, [Security defaults](security-defaults.md)).

The three others are each an issue of the spike:

- `CONFORMANCE_PLANS` names no `acr_value`, and one module sends one as the `acr_values` of a backchannel request; the parameter had nowhere to come from while the endpoint ignored it, and has one since heidi#266. One module of the poll run, which reports two more findings after it. Issue heidi#317.
- A client that registered to be called back reaches the token endpoint before it will answer. The eight modules of the ping run that need a request to be answered fail on the status the token endpoint returns, and the same modules of the poll run, which comes back at the interval it was given, pass. Issue heidi#318.
- A token request that holds no certificate is answered `authorization_pending` rather than refused. §5.2.2 asks for a sender-constrained token whichever way the client authenticated, and this provider binds a token to a certificate for a client that authenticated by it and for no other. One module per run. Issue heidi#319.

None of the three is a gap anybody decided to leave, which is what the `known` list is for: they are issues of the spike, open and worked on. The two runs therefore carry them under `waiting_on` instead, and what that does is in the docblock of `CONFORMANCE_PLANS`: their modules run, every result and every finding is printed, the run is named at the end with its issues and with the modules it did not pass, and it does not fail the task, so that the eleven runs the provider does pass keep gating in CI. The line is one per run and not one per module because what is missing is the provider's: naming every red under `known` would write one rule several times over, and every one of those lines would be wrong the day it is lifted. A run that passes whole with the line still there fails the task, which is what deletes the line.

### Key rotation

`oidcc-server-rotate-keys` is the one module of `oidcc-dynamic-certification-test-plan` the OP answers (the rest of that plan wants dynamic client registration and request URIs), and the external judge of the key rotation of spike 2. The suite has no plan for a single module, so `castor conformance` creates it on its own through `/api/runner`, with the configuration and the variant `server_metadata=discovery`, the only one it takes. The module reads the JWK Set at its creation and then waits for the operator to rotate the keys before it is started; the task runs `heidi:keys:rotate --now` on the OP in the operator's place, then starts it. The module reads the JWK Set again and passes when a new key is there and one of the former keys still is: the new key signs at once, the one that signed retires over its window (architecture §3.3). A run therefore leaves one more key in the JWK Set until that window closes. The page of the module is its log; there is no plan page.

The other plans of the suite are for what the OP does not have: `implicit`, `hybrid` and their `formpost` variants (decision 0006), `dynamic` (registration, `request_uri`), `session-management` (`check_session_iframe`) and `3rdparty-init-login`.

### Running them

`castor conformance` fills the placeholders of `tests/conformance/configuration.json` from those values, creates each plan through the API of the suite, runs every module (or those named by `--module`, a repeatable substring) and prints one result per module with the failures and warnings of its log, then a summary with the suite version and the URL of each plan page. The scripted browser of the suite signs in and consents by itself, following the `browser` section of the configuration; see `tests/conformance/README.md` for how it reaches the OP and the callback of the suite from inside its container.

Certification itself (the right to display the mark, the public listing) is submitted on https://www.certification.openid.net/ and is paid; testing there is free but needs an OP reachable from the Internet. `castor conformance --suite https://www.certification.openid.net` with `CONFORMANCE_TOKEN` in the environment runs the same plans there.
