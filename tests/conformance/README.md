# OpenID conformance suite

The suite runs locally from the prebuilt images of `registry.gitlab.com/openid/conformance-suite`, under the `conformance` profile of the root `compose.yaml`:

```bash
castor start --conformance     # OP on https://op.localhost, suite on https://localhost:8443
castor conformance             # every plan; --plan form-post for one (repeatable), --module oidcc-server for one module (repeatable, substring)
castor conformance --strict    # a WARNING fails too, which is what the CI runs on main
castor logs conformance-server
```

`server-entrypoint.sh` replaces the entrypoint of the suite image for one reason: before starting the suite exactly as the upstream image does, it makes the JVM trust two certificates. The internal CA of the Caddy instance serving the OP, so that the suite calls `https://op.localhost` like a browser does; and the self-signed certificate of the suite's own nginx, because the scripted browser of the suite runs inside that JVM and follows the redirect of the OP to `https://localhost:8443/test/a/heidi/callback`. Inside the container, `localhost` is the container: the `conformance-redirector` sidecar of `compose.yaml` shares its network namespace and forwards the loopback port 8443 to nginx (the suite does the same with `fintechlabs.startredir` and a `redir` binary the prebuilt image does not ship).

The suite version is pinned (`CONFORMANCE_SUITE_VERSION`, `CONFORMANCE_NGINX_VERSION` in `compose.yaml`). Certification results must name the version they were produced with; `castor conformance` prints it with the summary.

## The certification plans

Six plans and one module on its own, described in `docs/conformance-suite.md`: `oidcc-basic-certification-test-plan` (spike 1), `oidcc-config-certification-test-plan`, `oidcc-formpost-basic-certification-test-plan`, `oidcc-rp-initiated-logout-certification-test-plan`, `oidcc-frontchannel-rp-initiated-logout-certification-test-plan` and `oidcc-backchannel-rp-initiated-logout-certification-test-plan` (spike 4), and `oidcc-server-rotate-keys` (spike 2), the one module of the Dynamic OP plan the OP answers, created without a plan through `/api/runner` since the suite has no plan for a single module; the task rotates the signing key of the OP (`heidi:keys:rotate --now`) between its creation and its start, where the suite expects the operator to. One configuration serves them all; `castor conformance` runs them one after the other, `--plan` picks one.

`oidcc-basic-certification-test-plan` is created with the variants `server_metadata=discovery` and `client_registration=static_client`. The plan is a fixed list of modules, each with its own variant: every one runs with `client_auth_type=client_secret_basic` except `oidcc-server-client-secret-post`, and all with `response_type=code`, `response_mode=default`. Three registered clients serve them: `client` and `client2` (`client_secret_basic`, the second one is the wrong client of some modules) and `client_secret_post` (the one module that authenticates that way). The OP registers them in `apps/op/config/packages/heidi.yaml` as `conformance-basic`, `conformance-basic-second` and `conformance-post`, with the alias `heidi` in their redirect URIs (`https://localhost:8443/test/a/heidi/callback`) and `requires_pkce: false`, because the profile sends no `code_challenge` (decision 0008 of the design repository); `castor provision` generates their secrets into `apps/op/.env.local`.

`oidcc-formpost-basic-certification-test-plan` is created with the same variants and served by the same three clients: it is the Basic OP plan run with `response_mode=form_post`, where the OP answers with a self-submitting page instead of a redirection. The scripted browser needs no entry of its own, the page submits itself and lands on the same callback. Its 35 created modules end in 32 `PASSED` and 3 `REVIEW` since spike 5 brought request objects (heidi#161): `oidcc-unsigned-request-object-supported-correctly-or-rejected-as-unsupported`, which writes `response_mode` only inside the request object, was the one module listed as known, and the `known` list of the plan is now empty. It reads that object because `conformance-basic` registers `request_object_signing_alg: none` (OIDC Registration §2), which no other client of the OP does.

The two logout plans are created with `response_type=code` and `client_registration=static_client`, and each is served by a client of its own, `conformance-front-channel-logout` and `conformance-back-channel-logout`, which register the URI of their channel and of no other: the suite certifies one channel at a time, a client that registers a logout URI is told at every logout of its sessions, and a module of another plan then fails on a request it did not expect. The back-channel plan is the only one whose result depends on the worker, which posts the logout token: the `conformance-worker-redirector` sidecar of `compose.yaml` brings the loopback port 8443 of the suite into the network namespace of the worker, and `docker/worker/entrypoint.sh` adds the self-signed certificate of nginx to the trust store of that container, the way `server-entrypoint.sh` adds it to the truststore of the JVM. A worker that restarts leaves the sidecar forwarding nothing, so `--reset` restarts both.

`--reset` empties the database of the OP, provisions it again, restarts the containers and waits for the discovery document. The plans want the OP as `castor provision` leaves it, a development user with a password and nothing else: a second factor or a passkey enrolled by hand stops the scripted browser on the page that asks for it, and every module of every plan then fails on `unexpected url for task: Verify complete`. Only one run at a time, whatever the plan: the alias of the configuration is exclusive, and two runs at once interrupt each other.

`configuration.json` is the configuration of every plan. It carries no secret: `castor conformance` fills its `{PLACEHOLDERS}` from the environment of the application (`HEIDI_ISSUER`, the five `CONFORMANCE_*_SECRET`, `HEIDI_DEV_USER_PASSWORD`) and from the development user (`HEIDI_DEV_USERNAME`), then creates each plan through the API of the suite, runs its modules one after the other (the alias makes them exclusive) and prints the result of each with the failures and warnings of its log, then a summary and the URL of each plan. The exit code is 1 when a module is `FAILED`, `INTERRUPTED` or `TIMEOUT`, unless its plan lists it under `known` with the reason and the issue that closes it, in which case it is reported as `KNOWN` and accepted, and the run fails instead the day it passes; `WARNING` and `REVIEW` are for a human to read on the plan page before anything is submitted, `SKIPPED` is the suite's own choice. `--strict` moves `WARNING` to the failing side, which is how the CI reads the plans: a warning is a specification the provider answers less than it should, and it is not a state a submission may be in. `REVIEW` and `SKIPPED` stay accepted under `--strict` as well, no run of a plan can avoid them: fourteen modules end in `REVIEW` because they want a screenshot a human uploads: three of the Basic OP plan, the same three of the Form Post one, and eight of the RP-Initiated Logout one. `oidcc-unsigned-request-object-supported-correctly-or-rejected-as-unsupported` was skipped by the suite itself in the Basic OP plan as long as the OP answered `request_not_supported`, which the profile permits; since heidi#161 the OP reads the object, the module runs and it passes. `oidcc-ensure-request-object-with-redirect-uri` had an override of its own for the same reason and no longer needs one: it sends an unregistered `redirect_uri` in the query and the registered one inside the request object, so the OP used to refuse on the query before it read the object and showed its error page; it now reads the object, whose parameters are the request (OIDC Core §6.1), and answers a redirection to the registered URI, which the default entry of the `browser` section follows like any other.

The job `4️⃣ OpenID Conformance (Basic, Config, Form Post, RP-Initiated, Front-Channel and Back-Channel Logout OP)` of `.github/workflows/ci.yml` runs all of it after the tests: the stack is started on the runner, `castor provision` writes a fresh `apps/op/.env.local` and restarts the worker so that it holds the secrets just written, and the plans run with `--strict`. It is the longest job of the workflow and it costs about eight minutes: two to build the image and start the stack, and a little over six for the modules, measured on a development machine as 2 min 36 for the Basic OP plan, of which `oidcc-codereuse-30seconds` waits out its thirty seconds on its own, 2 min 35 for the Form Post OP plan, which is the same modules, 42 s for RP-Initiated Logout, and six seconds for each of the two logout channels. The runner starts from an empty database on every run, so `--reset` is a developer's option and the job does not pass it. It runs on the host and not in the phpqa image, needing a Docker daemon, and installs the application with its own lock, the way a developer runs it, the monorepo jobs being the ones that follow the dev branches of Symfony.

The `browser` section of the configuration drives the scripted browser of the suite (HtmlUnit, see the BrowserControl page of the suite's wiki): on the login page it fills `#username` and `#password` and submits, on the consent page it clicks `button[name=answer][value=allow]`, both optional because a module may find the user signed in or the consent given, then it waits for `#submission_complete` on the callback of the suite. A second entry drives the end session endpoint: it clicks `button[name=confirm][value=yes]` when the OP shows its confirmation page (an optional command, since a verified `id_token_hint` skips the page) and waits for `https://localhost:8443/test/a/heidi/post_logout_redirect`. The `override` section adapts it for the module that expects an error page on the OP instead of a redirect (`oidcc-ensure-registered-redirect-uri`: the text of the page fills the screenshot placeholder of the module, hence a `REVIEW` result) and for those that need a second login (`oidcc-prompt-login`, `oidcc-max-age-1`); the logout modules that end on the OP get theirs too, the signed-out page, the error page or, for `oidcc-rp-initiated-logout-bad-id-token-hint` whose hint the OP cannot verify, the confirmation page filling the placeholder, unanswered. An override replaces the whole `browser` array, which is why each of them repeats the authorization entry. A module the browser cannot finish waits for a human: the task prints the URL the suite exposes and waits up to five minutes.

Every run is recorded in the journal of `spikes/01-conformite/README.md` of the documentation repository, with the suite version.

## FIDO Alliance conformance tools

The FIDO Conformance Tools are a desktop application of the FIDO Alliance, obtained on request from fidoalliance.org (its version goes in the journal with every run); nothing of them runs in CI, the run is by hand, like the hosted suite of spike 1. The server tests of FIDO2 drive the four endpoints of the FIDO2 server API (`/attestation/options`, `/attestation/result`, `/assertion/options`, `/assertion/result`), which the bundle provides in `src/symfony/src/Fido/Conformance/` on the enrolment and the authentication of the core, with what the tools ask for and the product never does (the attestation conveyance, the authenticator selection, the extensions), the users created on their first ceremony. The application imports them in development only (`apps/op/config/routes/fido_conformance.yaml`, `when@dev`, the prefix `/fido/conformance`), as it registers the clients of the OpenID suite: they are not an API of the product. The tools are given `https://op.localhost/fido/conformance` as the server URL and append the four paths; they must trust the internal CA of Caddy, or be told not to check the certificate, and reach `op.localhost` (127.0.0.1 on the host that runs the stack).

The tools verify the attestation of their virtual authenticators against metadata, which the ceremonies read from the store of `heidi.webauthn.metadata_storage` (`/app/var/webauthn` in the op container, the anonymous `var` volume of the container, which `castor start` keeps):

- the metadata statements of the virtual authenticators, shipped by the tools (a directory of JSON files), copied into the container and imported as they are, unsigned: `docker compose cp <directory> op:/tmp/statements` then `castor console heidi:webauthn:mds-import /tmp/statements/*.json`;
- the MDS3 tests, whose blobs the tools serve from endpoints they list for the server URL given, signed under a test root: `castor console heidi:webauthn:mds-refresh --root https://mds3.certinfra.fidoalliance.org/pki/MDS3ROOT.crt --url <endpoint>` with every endpoint listed (`--url` is repeatable); a blob the tools sign badly on purpose is refused and printed as such, which is what those tests check;
- the real metadata service, for a run against real authenticators: `castor console heidi:webauthn:mds-refresh` alone downloads the blob of the FIDO Alliance (`https://mds.fidoalliance.org/`, which `https://mds3.fidoalliance.org/` redirects to; no outbound request follows a redirect) and verifies it under the GlobalSign Root CA - R3 the bundle ships. The service rate-limits: a refresh is a by-hand act, one per day at most.

A document of the store is read once per process (the workers of FrankenPHP restart on a source change, not on a write under `var/`): restart the stack after a refresh or an import, or the running workers keep what they read.

Which tests pass, which are skipped and why, go in the journal of `spikes/03-passkeys/README.md` of the documentation repository, with the version of the tools and the date, as the runs of the OpenID suite go in the journal of spike 1.
